# Pilot curation: a checked-in dictionary of human decisions

Extends ADR 0004. That ADR resolves what the data decides on its own and emits a reconciliation report; nothing consumed the report, so every rebuild re-flagged the same cases. This ADR adds a curated-overrides source the build reads and applies deterministically, so a maintainer's judgement survives every rebuild and the report narrows to only the still-undecided cases (issue #9).

## What the upstream id actually is

The `pilot` id is not an account number. 1221 of 1248 ids are drawn from a closed 22x20x20 vocabulary of `<Adjective><Colour><Animal>` names (`LunarRedFalcon`), and 90 carry a 3-hex suffix (`ShadowMaroonWolf1A3`). That suffix count matches the birthday-paradox prediction (80.9 collisions expected, 90 observed), and all 82 collided bases hold different display names: the id is a random per-registration pseudonym of a name string, and the generator broke its own clashes with the suffix. So the id is stable but neither one-account nor one-person: two people who share a name can hold different ids, and the same name can recur under many.

## The curation dictionary

`curation/pilots.toml` holds eight kinds of entry, each keyed only on a stable upstream identifier (a pilot id, a deck id, or an event code), never on a derived value like a display name or a synthetic key (`nan:darcy`, `LunarRedFalcon#2`) that shifts when data changes. That is what makes a decision timeless: recorded once, it applies identically to every future ingestion.

The first four are this ADR's; the last four were added by later work and are recorded here so the list stays the one place the whole vocabulary is written down.

- **merge**: collapse several ids onto one canonical id, flattened transitively (union-find), so `Alexadner J -> Alexander J` and `Alex J -> Alexander J` land on one node.
- **reject**: mark two ids as different people, suppressing the pair from the candidate report for good and, since issue #74, keeping them apart in the identical-name join should their display names later converge (ADR 0009 records the mechanism).
- **name**: pin a display name over the majority vote (`alejandrofp -> Alejandro D`).
- **deck_pilot**: reassign one deck to a real pilot id, resolving a null-pilot deck to its owner before the name vote.
- **split**: mark same-named ids as different people, keeping the identical-name join (ADR 0007) from folding them into one node. The inverse of a merge; ADR 0009 records it.
- **deck_archetype**: reclassify one deck whose source title mislabelled its archetype, collapsing it onto the single corrected engine (issue #9).
- **deck_event**: return one deck to the event it was really played at, for a deck the source stranded at a malformed event. The deck adopts the target cohort's event id, type and claimed field, and its norm is re-scored against the field the build counts (issue #167).
- **hold**: record that a pair was examined and could not be settled on the evidence available, with `settles_on` naming what would decide it and `as_of` naming the snapshot the reasoning was written against (issue #228). Alone among the eight it applies nothing to the graph: it neither merges, separates nor renames, so a build with every `hold` deleted produces the same graph. What it changes is the report, which splits the candidate list into *held* and *unexamined*, so the review queue stops re-presenting pairs a human has already reasoned about and the build's own count says how many questions are actually open. The build then re-evaluates every hold against the corpus it just ingested, so growing data does the review work rather than a human re-reading the list (see "Trigger evaluation" below).

  Since issue #232 a hold also takes a **single id**, which is the other identity queue's question: `under_merges` is several ids that may be one person, and `multi_name_ids` is one id whose decks recovered several surnames and may be several people (issue #39). Both are held by the one kind, because both are "examined, not settled" against a stable upstream id; a two-id entry expands to its pairs as `reject` and `split` do, and a one-id entry is kept whole, since it holds that id's own names open rather than any pair it belongs to. Only the settling conditions differ (below). No settling kind can contradict a one-id hold: every kind that settles an identity question keys on two ids, so none of them answers "are this one id's decks one person", and the kind that resolves it, `deck_pilot`, names only the id it moves a deck *to*. What a one-id hold can be is misaddressed. The queue reports the canonical id a merge leaves standing, so a hold naming a folded-away member examines nothing: the canonical stays on the queue as unexamined while the hold's own triggers, which do resolve the merge, can still announce a decision on that same id. That is refused at load time, exactly as a `name` pin on a merged id is.

An absent file is not an error: the heuristics alone still build a graph. A malformed file, or one that contradicts itself, aborts the build. Six shapes contradict: a merged group naming two canonical ids; a `name` pin on an id that merges away; a pair carrying both a `merge` and a `reject` or `split`; two `name` pins on one id (the merge/reject and double-pin shapes were added by issue #204, which found four such entries on file); a pair carrying both a `hold` and any of `merge`, `reject` or `split` (issue #228); and a one-id `hold` on an id that merges away (issue #232). Two `hold` entries on one pair are refused for the same reason as two `name` pins: file order would silently decide which condition the report carries, and the discarded one would be reported nowhere. The remedy the second one names is an edit, not an appended inverse: `merge` only ever exists for ids whose recovered names differ, which is the complement of what the identical-name join and its `split` and `reject` separators decide, so deleting a wrong `merge` is always sufficient and no precedence between the kinds is needed. The fifth is the same argument applied to the third state: a `hold` says "not decided" and the other three say "decided", so upgrading a hold means replacing the entry, never appending a decision beside it. The sixth is the second applied to the other kind that is looked up by a canonical id, and carries the same remedy: name the canonical.

A `hold`'s `as_of` is graded on its *shape* (`%Y%m%dT%H%M%SZ`, the name `fetch` mints), never on whether that directory is present. Presence is not a portable question: `snapshots/` is gitignored and each directory is named for the wall clock of the machine that fetched it, so the stamps differ in every clone and CI holds none at all. Checking existence at load time would make the one entry kind that applies nothing to the graph the only one able to stop the graph being built, on every machine except the one that wrote the entry, and it would invert the rule that a stale entry is reported and never fatal: a snapshot later pruned or re-fetched would turn a valid hold into a build abort. Whether a stamp names a snapshot a given build actually read is a real question, and it is answered at build time, where the ingested set exists: an `as_of` naming none of them is reported as a dead entry, alongside the entries that key on an absent id, and never aborts.

## Trigger evaluation: growing data does the review work

A hold names the condition that would settle it, so the build re-evaluates that condition on every ingestion (issue #230). Four triggers fire, and each reaches the reconciliation report with the fact that fired it, derived every build so it cannot go stale the way a transcribed count would.

- **`shared_event`** fires when the two held ids both registered at one event. It settles the pair, on the structural fact the wave 2/3 rules below rest on: two entries at one event are two people. Twelve of the twelve decisions in the 2026-08 round were exactly this. The `nan` sentinel a deck carries when the source lost its event is not an event and never fires it: two ids stranded under it share a hole in the data, which is the gap `deck_event` exists to repair (issue #167), not a registration.
- **`joined_name`** fires when the identical-name join (ADR 0007) folded the two held ids into one pilot. The join is right to fire, an identical recovered name being this project ruling on identity, but it takes the pair off the held list while leaving both raw ids live, so nothing else can report it and the entry would go invisible and un-retirable.
- **`event_split`** fires when a held *single* id registered at one event under two surname families. It is the same structural fact as `shared_event`, reaching the queue that asks about one id: one deck is one pilot's single entry at one event, so two entries there under two surnames are two people, and the event split (ADR 0004) has already numbered them apart. It settles the row, and where the row is the shadow of a `merge` (below), it refutes that merge. The families it reads are the ones that put the id in the queue, an initial and the word it stands for included (`Ari S` against `Ari Steel`): two registrations at one event are two people however plainly one name abbreviates the other.
- **`new_decks`** fires when either id has gained a deck since the snapshot `as_of` names. Nothing is settled, but the evidence the reasoning was written against has moved, so the pair is up for a re-read. It is the one trigger a build cannot always evaluate: a delta needs the baseline the stamp names, and by the paragraph above that stamp is absent from most machines. So on a clone that did not read it, `new_decks` is silent for that hold and the same report carries the dead entry saying why. The asymmetry is the intended one. The two decisive triggers read only the corpus in hand and fire identically everywhere; the soft one declines to invent a baseline it does not have, and says so rather than reading as "nothing moved".

Both decisive triggers say so where their shared premise bends. One entry per pilot per event is a 4571-in-4634 regularity rather than a law (the wave 2/3 rules below carry the measurement), so where an id under a fired trigger is one the source itself registered at an event twice, the detail carries that. The trigger still fires: the evidence has still arrived, and suppressing it would park a hold nothing else reports, which is the hole issue #230 exists to close. What changes is that the line the decision is made on reads as evidence rather than as a verdict. It is read off the *raw* upstream id and never the pilot an id resolves to, because a `merge` or the identical-name join puts two ids' decks under one pilot by construction: that is this project ruling on identity, not the source testifying about how a human enters events.

The other two triggers have no single-id shape, for the same reason in both cases: each is a fact about two ids meeting. `shared_event` needs a second id to share the event with, and the structural fact under it survives as `event_split`, asked of one id's own two names instead. `joined_name` fires where the identical-name join folded a held *pair* onto one pilot, which is that pair's question answered; the join folding a held single id into another pilot answers nothing about whether that id's own decks are one person, because the question travels with the decks. So a pair is watched by `joined_name`, `shared_event` and `new_decks`, and a single id by `event_split` and `new_decks`.

What a fired single-id trigger hands a maintainer is also a different decision. There is no second id to `reject`, so the resolutions are a `deck_pilot` moving the minority decks to their real owner, or, where the row is the shadow of a `merge` (see Consequences), reversing that merge. Both need a target id to exist, which is why a row can be settled by the data and still not be actionable the same day.

Each id is read at the pilot it resolves to, not under the raw id the entry names, because a `merge` or the identical-name join can fold a held id away and its decks are its canonical's from then on. Holding a pair while merging one of its ids into a *third* is not the contradiction the loader refuses, which is why this is an ordinary shape rather than a defensive case: the merge decides that id against the third and says nothing about the pair.

Every trigger is evaluated against every hold, not only against one whose `settles_on` names it. A shared event is a fact about the data rather than about what a human guessed would settle the pair, so gating it on the guess would leave a decided pair parked because the guess was different. `settles_on` is carried into the report and never consulted.

Firing is evaluation and never application. It reports that the evidence to decide a pair has arrived; the decision is still a human's, recorded as an edit to the dictionary, so a build with a fired trigger produces the same graph as the same build with the `hold` deleted. What changes is the report and the console: a settled pair is an available decision sitting unmade, so it takes the banner treatment a flagged record gets rather than a line a scrolling log buries, while a moved one is counted.

## Wave 1: only hard facts merge

The heuristics find and rank candidates but never merge two ids on their own. A recovered name is classified by how two names relate: `exact`, `first-name` (a bare first name against `First I`), `handle` (`OdeB` against `Oden B`), `nickname` (`Chris`/`Christopher`), and `typo` (one Damerau edit, so `Alexadner`/`Alexander` but not `Jake`/`Jack`). None of these is a hard fact of identity: two different people are reasonably named `Connor P`, a bare `Noelle` may be a different Noelle, and a handle is lossy (`JonB48` fits any `Jon* B`). So in wave 1 every name-similarity match is a proposal a human confirms into the dictionary; only the dictionary merges ids. (ADR 0007 has since carved out the `exact` shape: identical recovered names join automatically on every build, with `split` (ADR 0009) as the curated override, so only the non-identical shapes remain proposals.) Deck or archetype similarity is not a tie-breaker either, because teammates share lists, so decklist overlap cannot prove identity; it is shown in the review report as evidence only.

## Duplicate registrations

Two decks that share an upstream id, an event, a recovered name, and a card-for-card identical list are one registration entered twice (teammates share a list but not a name). The build keeps the best placement, drops the rest, and logs each drop in the report, so the deletion is never silent. This is the one deletion wave 1 makes automatically, because exact-identical-under-one-name is a hard fact. Near-identical lists are left as report candidates, not deleted.

## Title parsing corrected

Name recovery previously misread several title shapes. A leading `*` or a `Top N` cut is a placement, not a name; a name that is only a points marker (`8pt Blue Moon`) means the pilot field was empty; and a separator-less title (`1st Ben N Lurrus Breach PoGTeams2024`) is split by subtracting the source's own deck name and event from the tail. A placement the source left null is also recovered from the title, taking an explicit range's best rank (`5th-8th` reads as 5, the source's own convention 573 of 573 times, issue #103); a `Top N` cut is read off its event's cohort instead (`resolve_cut_placements`), so CanBrawl2's four `Top 4` decks read 1st and its four `Top 8` read 5th. The source value always wins when present.

## Wave 2/3: adjudication heuristics

Wave 1 hands every name match to a human. These patterns let a maintainer decide in bulk; each still records its verdict as a dictionary entry keyed on upstream ids. "Overlap" is the maximum card-set Jaccard across the two ids' decks (7PH decks are singleton, so a deck is a set).

Three rules govern every pattern below. The 2026-08 round settled them and issue #229 records them, so that the next round does not re-propose the same pairs on the same misleading numbers.

**A pair resolves on a structural fact, not on a similarity score.** The one structural fact this data carries is the event: a deck is one pilot's single entry at one event, so two ids that both entered one event, fielding different decks, are two people. That is the strongest regularity in the corpus rather than a law, and it is worth knowing by how much: one upstream id enters one event exactly once 4571 times and more than once 63, and the exceptions concentrate at the large multi-flight events (5% of the ids at NHC26, 4% at NHC24 and NHC25, against 1% at ETEAE). So the fact decides, and it decides less about an id the source itself entered twice. Both settling triggers carry that caveat into the fired hold's own detail (`pilots._repeat_entrants`), which is the only place it is worth anything, since it is the line a maintainer decides on. All twelve decisions the 2026-08 round recorded rested on the event, and none on a similarity score. Every shared event involved was a single Tournament, and the highest shared-event overlap across the twelve was 0.28. The separators below are that one fact in its several shapes, which is why they decide while the overlap clauses only propose.

The escape hatch, that one person can play two flights under two spellings, survives but changes hands: it is what a proposed *merge* now has to establish, rather than a doubt that keeps a shared-event pair open. Eleven of the twelve shared a single event, and what separated each was the absence of any positive case for one person entering twice, whether a weak name link (a handle, a bare first name, a substitution reaching another real name), a lopsided or independent deck record beside the shared registration, or no overlap anywhere to explain. Three merges on file cross a shared event, and what carried each was an argument for identity that never leans on the shared-event overlap. One is a name shape that cannot be two real people: an insertion, deletion or transposition scrambling a name into a non-name (`Zachary M` = `Zachaery M`). The other two are single-deck numeric handles threaded onto an established career by a 1.00 decklist match at *adjacent* events, not at the shared one (`JamL9` = `James L 2`, `DanS109` = `Dan S 2`), and two facts carry them rather than the overlap on its own. First, the established side is in both cases a demonstrated repeat entrant, so the premise the separator rests on is one that id visibly breaks and the two-flights reading is evidenced for it rather than merely available: the source has `Daniel S` entering twelve events more than once, three times at ETEAE and twice at the SydneyShowdown it shares with `DanS109`, and `James L` twice at each of BazaarInvi and VFNIQ. Second, the exact list clears the matched stranger ceiling for its own archetype, which is the baseline rule below applied to a 1.00 rather than a new rule: `JamL9`'s 5c Walks is 1.00 to `James L`'s own and 0.76 to the nearest stranger's, `DanS109`'s Breach list 1.00 to `Dan S`'s and 0.83 to the nearest of five strangers on Breachbond. That second margin is the thinner one, Breachbond being a real netdeck, which is exactly what the separator below reads a 1.00 as; what separates the two readings is that here the 1.00 sits above what the room scores rather than level with it. Overlap at the shared event itself cannot do this work in any case, because one person's two decks at one event overlap about as little as two strangers' (0.07 and 0.25 in the worked case, against 0.03 for the strangers).

**Similarity is admissible only against a matched stranger baseline.** A raw overlap means nothing without the population it sits in, and the convenient population lies. *Matched* means distinct pilots on the same primary archetype and the same colour family, separated by a date gap comparable to the one between the two decks under test. What decides is where the pair falls in that distribution, never the overlap on its own.

| pair | overlap | broad pool | matched pool |
| --- | --- | --- | --- |
| Bradley H / Brad H, BG Lands | 0.721 | p99 | p88, 185 stranger pairs at or above |
| Brint G / Brent G, Grixis | 0.596 | not run | p46, the median stranger |

That p99 was an artefact of pooling Lands variants across four years: lists drift, so a pool spanning years understates what strangers score and flatters every pair measured against it. This is the test the file's `Angus M != Angus McC` entry established (80th percentile matched, against the 92nd an all-time pool suggested), now confirmed on a second archetype and pointing the same way.

**The loss is asymmetric, and it breaks ties.** A false merge fuses two people irreversibly for every metric downstream, and the event split cannot undo it because it keys on one id. A pair left apart costs one row in a review queue. So a pair the evidence does not resolve is recorded as a `hold`, never merged on the strength of a number.

Together the baseline and the asymmetry narrow both overlap bars below: ~0.5 on a shared archetype at disjoint events is the floor that admits a pair to the matched-baseline test, not a reason to merge it. That is why the round recorded zero merges, all three candidates clearing the naive 0.5 bar having failed the baseline. A round can be thorough and still land no merge, so "no merges this round" is a result here, not a round that was skipped.

Same person:

- **Single-deck slip.** When the rarer side has exactly one deck, it is a one-time data-entry slip at a single event. If that lone deck shares an archetype with the matching name and overlaps at least ~0.5 on disjoint events, it is the same person. Confirmed by hand down to 0.63; the overlap floor is the safety, excluding low-overlap namesakes. *Narrowed by the matched-baseline rule above: clearing the floor now opens the test rather than settling it, since a single deck is also the case with least to match against.*

Different people:

- **Shared-event separator.** Two distinct ids that both register at two or more events are two humans: one registration per person per event, and at each shared event they field different decks. A single shared event is not enough on its own, because one person can play two flights under two spellings. *Narrowed by the burden shift above: the two-flights reading is now something a merge has to argue for, so a single shared event separates unless a merge makes that argument, and the shapes enumerated here and below are worked cases rather than the whole permitted list.* A single shared event with different decks *does* separate when the overlap driving a proposed merge comes from a netdecked archetype at *other* events and the name link is weak (a handle or a bare-initial surname stub): that overlap is community list-sharing, not identity. Do not merge across it in the hope that the event split will re-separate the ids by placement (ADR 0004) later; the split keys on one id, so once merged the two people are fused before it runs. An independent blind re-derivation (issue #9 audit) caught several such over-merges that forward candidate review had accepted as corroborated.
- **Single shared event, two further shapes.** The clause above needs a weak name link, a handle or a bare-initial stub, and two decisions on file separate across one shared event without one (issue #208 found them uncovered). A **borrowed list**: a lone deck reproducing an established pilot's own signature at an event that pilot also entered with a different deck (`Ben H 1` at 22 decks against `Benjamin H`'s single one, 0.97 on the Taxes list at ANZSS11). And **two careers just under the both-established floor**: `Alex B` at 7 decks and `Alexander B` at 3, both registering Jund at RC6, overlapping 0.39 on the shared list, which the separator below misses only for wanting four decks on each side. In both the name link is a nickname, so what separates is the deck record beside the shared registration, lopsided in the first and independent in the second, rather than the name being weak.
- **Both-established separator.** Both sides carrying four or more decks yet overlapping below 0.5 are two independent careers. A real alias shares a deck signature, and a one-time typo does not accumulate its own multi-deck career.

Traps that defeat the name shape:

- **Handle collision.** A handle is first-three-letters + surname initial, which collides across people (`CalT` = Caleb / Calum / Callum, `DanT` = Dan / Daniel / Danny). It is never structurally certain and must earn a merge by deck overlap like any other shape. Treating handles as structural once chained three distinct people at ~0.05 overlap.
- **False-friend names.** An edit-distance-1 match can be two different given names, not a typo: Andrea / Andrew, Antonia / Antonio, Jose / Rose, Bill / Will (distinct William nicknames). The `typo` shape cannot tell these apart, and high deck overlap does not rescue them, because teammates net-deck identical lists (ADR 0005): a 1.00 hit at non-shared events, with different decks at the shared ones, is list-sharing, not one person.

  The **edit type** is what splits the typo bucket for batching. A single insertion, deletion, transposition, or diacritic/punctuation change scrambles a name into a *non-name* variant of itself and cannot reach a different real name in one step (`Niocholas`, `Geroge`, `Trisitan`); these are same-person, subject to the corroboration caveat below. A single **substitution** is the danger zone: it flips gender or identity at any length (Tim / Tom, Antonia / Antonio, Dan / Ian) and needs a human. And when the substituted letter is the *surname initial* rather than the first name, it is simply a different surname and a different person (Matt A / Matt B, Charlie B / Charlie M). Short insert/delete false-friends exist too (Joe / Jose, JD / Jed), so restrict the insert/delete auto-merge to names of five or more letters.

When a merge does land, the canonical id is chosen for the best display name, not the largest deck count: prefer the correct spelling and the real full name over a busier misspelling or a handle (`Gerard N` over the busier `Gerad N`; `Jinghao Y`, `Chia Wei L`). Because the merged node's display name is a per-deck majority vote, a merge onto a low-deck real name may need a `name` pin to stop a busier handle winning the vote (`AarW15` back to `Aaron W`).

A **name-only merge needs deck corroboration.** "The variant is a non-name, so it must be this one real bearer" is sound only when a deck overlaps to back it; with the decks actively disjoint (`Geroge H` at 0.04, `Axexander G` at 0.10) it is an unfalsifiable name bet, and those are held, not merged. The safe auto-merge bar is a same-name shape with overlap at least 0.5 on a shared archetype at *disjoint* events; a shared event is the teammate/event-split signal and is held. *Narrowed by the matched-baseline rule above: that bar is now necessary and not sufficient, and the "held" in both sentences is the `hold` kind, an entry on file rather than a pair quietly left alone.*

## Consequences

The reconciliation report now distinguishes uncurated candidates from already-decided ones and lists dropped duplicates, so the human-review list shrinks as decisions accrue. Since issue #231 that list is empty rather than merely shrinking: one pass read every candidate still open and recorded each as a `hold`, so an unexamined pair now means a pair this ingestion introduced. Issue #232 did the same for `multi_name_ids`, so the invariant covers both queues; `tests/test_build.py::test_nothing_in_either_identity_queue_is_left_unexamined` is what holds it, and each pass's own account of what it ruled out is in the dictionary beside the entries, not here.

That second pass found what the multi-name queue is mostly made of: 25 of its 28 ids owe their several surnames to a `merge` already on file. The scan reads each id *after* this dictionary is applied, so a merge folding `Ari Steel` onto `Ari S` leaves one id recovering two surname families and re-poses the question that merge answered. Two ids carry several surnames from the source alone, and one owes its second family to a `deck_pilot`'d null deck whose title left an archetype word where the surname goes. This is why the pass landed 28 holds and no decision: for 25 the decision exists with its evidence, and re-deciding it from that same evidence is not a second opinion. What the holds buy is the watch, since `event_split` firing on one of them would refute the merge behind it. Narrowing the scan so a curated merge does not re-pose its own question is deliberately *not* done here: 13 of those ids would then surface in `unexplained_names` instead (6 rows today, 19 after), which is a queue no pass has swept, so the change moves work rather than removing it and belongs with a sweep of that queue. The append-stable threading of a split id's decks into careers (replacing ADR 0004's placement-rank dealing) is deferred to a second wave; ADR 0010 has since delivered it.
